## 1. The researcher's instruction, recorded

In the 2026-10-16 session the researcher stated, as an instruction to the engineering agent, that (1) the annotations have already been approved, (2) full authorization has already been granted, and (3) they do not want to be asked to approve the same items again; the work is to proceed subject to the approved protocol and physical railway safety restrictions.

**Provenance and limits of this record.** The statement was given in a chat session. It is an explicit researcher instruction and is treated as such: it is not discarded, and nothing in this report asks for it to be repeated. It is **not** a cryptographic or external attestation, it names no events, no stage, no artifact hashes and no date of an earlier approval, and the repository contains no machine-readable artifact that corresponds to it. Software therefore cannot verify it, and this report does not represent it as verified.

Two further latent defects were found and fixed:

1. `STAGE21_PROMOTION_VALIDATION_REQUIRED` was appended unconditionally whenever all records were Stage-2.1. The gate may not open media, and the promotion check needs media, so the gate **could never become ready even with perfect evidence**. It is replaced by a hash-bound *promotion receipt* issued by the media-hashing readiness CLI (`readiness_cli --receipt-path`, written only on READY, refused inside protected trees) and verified by the gate without touching media.
2. Split and R04 decision artifacts accepted any non-empty `decided_by` string. They now require an identity on `data/ground_truth/authorized_reviewers.json`, a verbatim `researcher_statement`, and a non-future timezone-aware timestamp; the manifest must also equal the decided split and camera scope.

## 5. EVAL-AUTH: what is and is not verifiable

`data/governance/eval_authorization.json`, schema `phase12-eval-authorization/1`. The verifier checks, with no caller flags honored:

| Property | Check | Verifiable? |
|---|---|---|
| Named authority | `authorized_by` is on `data/ground_truth/authorized_reviewers.json` | Yes (convention-level; the allowlist is a text file) |
| Exact field set | Unknown keys (`ready`, `approved`, `eval_auth`, …) are refused | Yes |
| Self-consistency | `record_sha256` = canonical hash of the rest | Yes |
| Scope | `operation == phase12_official_evaluation`, stage equals the promotion receipt's stage, `field_or_physical_operations_authorized` must be `false` | Yes. Physical/field operations can never be authorized by this artifact |
| Evidence binding | Seven SHA-256 bindings must equal the *live* artifacts (frozen config, decision policy, input manifest, split decision, R04 decision, protocol profile, promotion receipt) | Yes. Changing any evidence after the statement voids it (`EVAL_AUTH_BINDING_MISMATCH`) |
| Attestation | Only `RECORDED_RESEARCHER_STATEMENT` with `signature: null`; any signature-style attestation is **refused**, not trusted | Reported honestly as `recorded_statement_unsigned` |
| Who typed the file | `recorded_by.kind` is `researcher` or `agent_transcription` (the latter requires `transcription_source`) | **No.** Nothing in the repository can prove authorship; the level is surfaced in every report as `authorization_is_cryptographic: false` |

This follows the project's existing convention (`configs/exploratory_dual_camera_v1.1.0_authorized_20261013.yaml`: verbatim statement, named authority, date, exact scope, pinned hashes) and adds the binding and the strictness the earlier record lacked. It is not self-approving: the bindings require a promotion receipt (itself requiring genuine Stage-2.1 records and the media-hashing gate), allowlisted split and R04 decisions, and a manifest derived from them. None exists today, so **no valid EVAL-AUTH can be written today**, and none was written. Once those exist, the researcher's already-given authorization can be recorded as an `agent_transcription` of their statement, so no new approval is requested.

## 6. What would make the gate recognize the researcher's approvals

These are production steps for evidence the researcher says exists in some form; none is a request to re-approve.

1. **Annotations.** If approved Stage-2.1 records exist outside this checkout (another session or tool), place them at `data/ground_truth/reviews/<cohort>/<event>_review.json`; the gate and loader will recognize them if valid. If the approval was given only in conversation, the records still have to be produced with the existing review/adjudication tooling, because the schema requires the observed-media hashes and session data that conversation cannot supply.
2. **Promotion receipt:** `python -m railway_detection.annotation.readiness_cli --receipt-path data/governance/stage21_promotion_receipt.json` (opens media; separately authorized workflow).
3. **Decisions:** `phase12-event-split-decision/1` and `phase12-r04-scope-decision/1` need `decision_status: APPROVED`, `decision_id`, allowlisted `decided_by`, `decided_at_utc`, verbatim `researcher_statement`, plus `partitions` / `event_modes` + `accepted_sync_events`.
4. **Manifest:** `build_evaluation_input_manifest(...)` from those decisions.
5. **EVAL-AUTH:** record bound to the `live_bindings` printed by `evaluation status`.

**Legacy disposition (LEG-EXEC) is a different item and is *not* covered by the general authorization.** `docs/PHASE11_6D…` requires the authorization to name the pinned proposal hash `41cbbba3e9d587b9972c3baca1b39f09d478d408d9c60fd538c249c4600113d4`, exactly the 27 sources, exactly the 28 outputs and the write operation. A general statement does not meet that rule, and this batch was also told not to modify the protected review records, so no notices were written. The 27 files remain refused by the loader and the gate regardless.
