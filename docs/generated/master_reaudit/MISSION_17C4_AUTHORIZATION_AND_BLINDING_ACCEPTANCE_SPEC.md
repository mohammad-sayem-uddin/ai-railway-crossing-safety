## 1. Trust profiles and exact authority subjects

AB01. An implementation must select COOPERATIVE_LOCAL or PROTECTED_BROKER explicitly. The former coordinates cooperating clients and detects differences against a trusted expectation; it promises no hostile same-user, direct-opener, administrator or rollback resistance. The latter requires a separately administered authority and resource broker outside the declared client's write capability. Neither is deployed or implemented in 17C-4/17D/17E. A compromised authority cannot attest to its own recovery; an independently approved recovery checkpoint and re-enrollment are required. Integrity availability and human truth are separate properties.

AB02. Seven role responsibilities are typed separately: FIRST_REVIEWER, SECOND_REVIEWER, ADJUDICATOR, PI_APPROVER, GRANT_ISSUER, PROMOTION_OPERATOR and ADMINISTRATOR. A promotion approval is a PI_APPROVER action or explicitly delegated approval, distinct from the publication operator action. Role membership never implies another role. A stable human principal may hold multiple appointed roles only under an explicit R05 overlap/conflict/recusal policy. Unknown policy, self-approved elevation, missing qualification or an unresolved required independence conflict denies the action. First and second reviewer must be distinct verified humans, including across aliases/shared accounts. No identities or appointment records are created here.

AB03. ApprovalRecord is a closed object: schema_version, approval_id, project_id, subject_kind, subject_id, subject_digest, approving_principal, approving_role, delegation_ref or null, operations, resource_ids, purposes, quotas, allowed_role_combinations, valid_from_utc, valid_until_utc, revocation_version, policy_binding and attestation_ref. Arrays representing sets are sorted/unique. Every reference resolves to independently trusted immutable content. Attestation validates exact subject bytes and authorized approval provenance; an unkeyed digest or text name cannot supply authenticity. subject_kind distinguishes APPOINTMENT, PROTOCOL_ADOPTION, ENGINEERING_SCOPE, REVIEW_PLAN, PILOT_PLAN, PROMOTION_BATCH and EVALUATION_RUN. No approval template is populated with real or placeholder credentials.

AB04. ProjectBinding contains project_id, approved repository identity (canonical remote/project identifier), approved commit, execution_manifest_digest, deployment_id and allowed relocation policy. The execution manifest enumerates exact module/package/config/dependency/policy digests, interpreter/runtime identity, entrypoint and protected input resolution rules. A filesystem root is a location, not project authority; relocation is permitted only by the binding's explicit policy. A trusted validator compares against the approved manifest and protected loaded execution provenance. HEAD, clean Git, index tree and hashing arbitrary startup files are insufficient for hostile-user enforcement. Unknown loaded provenance denies the protected profile; cooperative deployments disclose this limitation.

AB05. Grant is a closed versioned object: contract_version, grant_id, unique nonce, issuer_principal, issuer_role_binding, approval_record_ref, approval_record_digest, project_binding, protocol_binding, configuration_binding, dependency_binding, policy_binding, human_principal, appointment_refs, operations, resource_ids, purposes, case_assignments, quotas, not_before_utc, expires_at_utc and nonce_lease_policy_ref. Session ID/fence is bound atomically at reservation, not retroactively trusted from caller text. ProtocolBinding identifies adopted authority/version/path/content digest. Approval and subject scopes must contain the entire grant scope; unrecognized fields/versions, missing references, wrong project, stale policy or widened scope deny. All clocks use authenticated authority time with not_before ≤ now < expires. Lifetime/entropy/delegation values require T01; none is invented here.

AB06. Per-operation requests bind operation_id, request_digest, actor, role, grant_id, session_id, fence, case_assignment_id, operation, exact resource_id, purpose and expected authority version. Authority checks current appointment, approval, grant, revocation/time, execution/protocol/config bindings, case phase, quota and lease before allowing use. Unknown or unavailable authority state denies. Canonical resource handles must resolve within approved identity scope at the protected broker; path/symlink changes cannot substitute an unapproved resource. Check-and-use must be one broker capability boundary or an expressly limited cooperative operation.

AB07. One grant reserves one session using a durable atomic unique(grant_id,nonce) constraint. The same authenticated initialization request returns the same session; a different session/request cannot acquire it. Reservation consumes the grant before first access. ACTIVE may repeat permitted operations only within approved case/resource/phase/quota limits; fresh operation IDs never replenish quotas or authorize another first pass. Request retries with the same ID/content return the existing outcome; changed content conflicts. Close/abort/recovery never unreserve. A corrected observation counts according to the explicitly adopted quota policy, never an implicit exemption.

AB08. Approval of a role elevation must come from an independently authorized principal; administrator/issuer cannot approve their own elevation. Case-specific overlap and batch-approval oversight are evaluated against adopted R05 rules, rather than assuming all researchers may self-approve or silently mandating a new universal two-person policy. A reviewer onboarding change cannot expand the issuer registry. Missing issuer trust or delegation chain denies issuance. No token is issued or consumed by these specifications.

## 2. Irreversible human knowledge and observation phases

AB09. A CaseAssignmentKey is (project_id, canonical_physical_event_id, appointed_principal, review_round, assignment_id). A stable actor/event knowledge record spans sessions and aliases. States are ASSIGNED_UNEXPOSED → BLIND_DRAFT → BLIND_SEALED → COMPARISON_EXPOSED → CLOSED, with an orthogonal ABORTED terminal outcome; no transition restores UNEXPOSED after any disclosure. Assignment creation consults all prior exposure records for that actor/event. Restarting after exposure can produce a disclosed informed review, never a newly certified blind pass. Human external exposure cannot be proved absent by software; recorded disclosure and governance limits remain mandatory.

AB10. FIRST and required SECOND observation seals are independent; neither reviewer can load candidate/prediction/prior-review content through queue order, asset names, player state, logs, errors or API before their own seal. Case comparison release additionally requires both assigned independent seals, or an explicitly recorded no-second-required trigger/audit decision under the adopted risk policy. Global unrestricted OS/external-player blinding is not claimed. No trigger-policy adoption or universal dual review is inferred.

AB11. Observation bodies contain immutable observation_id, assignment_key, principal/appointment/authentication references, phase_at_capture, exposure_record_version, camera/capture/clock, boundary taxonomy, exact raw lexical input and normalized value, PTS/frame/timebase provenance, censor reason/direction, rationale, protocol/schema/source bindings and start/end timestamps. OBSERVABLE requires a value and evidence; other states cannot invent a point. T2 remains landmark-deferred. No global front/back ordering is imposed without approved same-clock evidence.

AB12. Corrections are new immutable records with correction_id, supersedes_observation_digest, original_blind_digest, capture_phase, exposure_version, reason, changed_fields, corrected_content and actor attestation. Original bytes and the blind-original view remain queryable. A post-comparison correction is permanently tagged INFORMED_CORRECTION. The effective corrected view may change only under adopted analysis policy and must report which original/exposure state it derives from; it cannot relabel informed data as blind. Semantically duplicate FIRST submissions for the same assignment are rejected even under fresh operation IDs. Administrative spelling correction and substantive re-observation remain distinguishable.

AB13. Adjudication is a separate immutable record binding exact sealed/corrected source digests, appointed adjudicator/conflict decision, applicable evidence and rationale. Unresolved remains UNCERTAIN. Automatic averaging/forced agreement/overwriting is forbidden; independently observed values may coincide with arithmetic midpoints. Active8.1 and proposed8.2 do not become interoperable by fabricating APPROVED or proposal hashes. Any schema extension for new censored/not-observable adjudication outcomes requires R01 and a tested versioned adapter before actual use.

AB14. Mandatory six risk categories remain the pending source policy: explicit review flag, UNCERTAIN, engine T3/T4 interpretation, front/back conflict, hash inconsistency/missing evidence, corrected/unverifiable candidate. Censored alone is not a trigger. Unknown trigger input blocks a declaration of fully evaluated review. Required second review and separate adjudication retain both source histories; human agreement cannot cure wrong media identity.

## 3. Exact promotion and permission boundaries

AB15. PromotionBatch is closed and content-addressed: batch_id, project/protocol/schema/adapter bindings, sorted cohort-qualified output identities, exact source ledger heads and observation/correction/adjudication digests, trigger/appointment/conflict evidence, deterministic output digests and policy digest. ApprovalRecord.subject_digest binds this batch digest, not a free-form event count. Authority reserves a unique batch/content ID; same ID/different bytes conflicts. Publish staged immutable qualified objects create-only, then one protected atomic visible batch manifest/receipt. Readers trust only manifest members; an uncommitted staging prefix is never GT. Crash/revocation semantics follow RC01–RC09. The present promoter is not claimed to implement these obligations.
