## 1. Registry identity and lineage

**CV01 — exact constructed registry.** Public APIs require exact SyntheticDataset with dataset_id, nonblank version, immutable tuples of PhysicalEvent, Capture, Asset and Annotation. All identities/provenance references use the explicit synthetic namespace; labels use the component's nonempty alphanumeric/dot/underscore/colon/hyphen grammar. Namespace and provenance strings assert no authenticity. Empty event registry, wrong record types, duplicate registry keys or missing source joins raise InvalidInput (ValueError, status INVALID_INPUT), with no accepted allocation. Input records remain caller-owned references; derived groups, aliases, canonical content and digests are recomputed. Public calls do not accept caller-created ValidatedDataset as a trust shortcut.

**CV02 — originals and derivatives.** Every event needs at least one original asset and original annotation union exactly equal to its event labels. A derivative DAG must be acyclic, parents present, and every parent-child edge resolve to the same canonical event. Multi-parent derivation is allowed only within that event. Descendants preserve event role by membership in that group. Annotation IDs cannot be shared by multiple assets; orphan/missing/wrong joins reject. Group weight counts originals, not inflated derivative count.

**CV03 — duplicates.** Repeated IDs and ambiguous alias collisions reject; never silently reassign identity. Same supplied content_identity across different canonical events rejects as unresolved; never silently merge events. Same content identity inside one event may be represented, and separate original asset records still count separately: no deduplication or near-duplicate discovery is implemented. The caller must settle actual identity upstream. No image/perceptual hashing is authorized. Canonical aliases resolve before allocation and outputs use canonical event IDs only.

## 2. Role and policy boundaries

**CV04 — role separation.** Only DEVELOPMENT_POOL groups enter allocation. CALIBRATION_ONLY, RESERVED_CONTROL, CASE_STUDY and FINAL_DESCRIPTIVE stay outside development folds. The final-descriptive role does not itself approve confirmatory evaluation. Camera/session/label/naming does not confer role eligibility. One group stays in one fold regardless of captures, cameras, originals, derivatives or annotations. Same camera/crossing may occur in multiple events/folds: this is event grouping, not leave-camera-out validation or proof of independence.

`role_plan` selects exact outer_fold, derives its evaluation group and complement, and requires validation_events within the complement with nonempty residual training. Empty inner validation requires an explicit synthetic frozen_rule_id. NONE, RESERVED_CALIBRATION and INNER_OOF are named calibration modes. RESERVED_CALIBRATION requires calibration-only events; INNER_OOF requires inner tuning but calibrator fitting with unverified OOF evidence still denies. Frozen rule IDs are declared metadata, not signed adoption.

**CV05 — full request binding.** `allocation_policy` constructs canonical AllocationPolicy: exact integer K≥2 (no hidden upper cap), canonical required_support=(label,positive-int-minimum) tuples with no duplicates, positive integer node_budget (default100000), profile SYNTHETIC_GROUPED_V1, search_limit18, objective LEX_EVENT_LABEL_ORIGINAL_SQUARED_IMBALANCE_V1, role_policy CANONICAL_EVENT_DEVELOPMENT_ONLY_NO_FALLBACK_V1, allow_ungrouped_fallback=False exactly, schema SYNTHETIC_ALLOCATION_POLICY_V1. bool/float integers reject. Same profile string with different K/support/budget is a different request. Do not reuse receipts under changed policy or reconstruct expected policy from a candidate. Every fallback request other than exact False rejects. ## 3. Algorithm, outcomes and receipt acceptance

**CV06 — deterministic feasibility.** Validated development groups are ordered by descending original count then canonical ID. Greedy evaluates K choices using sufficient statistics and lexicographic squared imbalance (event count, per-label count, original count), tie-breaking by fold. It verifies nonempty folds and required per-fold label support. This objective guides the heuristic; it does not promise the global optimum. Greedy failure at≤18 events invokes deterministic bounded first-feasible DFS with fold symmetry reduction/support pruning; larger failure is undetermined. No random seed or ungrouped fallback substitutes for constraints.

| Status | Meaning / accepted assignment |
|---|---|
| FEASIBLE_GREEDY | Verified greedy feasible assignment; objective and sorted event-fold pairs present. |
| FEASIBLE_SEARCH | First verified feasible search solution within budget; no optimum claim. |
| INFEASIBLE_NECESSARY | Too few groups/nonempty folds or total label support; assignments empty, objective None, reason present. |
| INFEASIBLE_EXHAUSTIVE | All canonical branches exhausted without feasible solution in bounded domain; assignments empty. |
| UNDETERMINED_SIZE | Greedy failed and development count>18; no accepted assignment, not an infeasibility proof. |
| UNDETERMINED_BUDGET | Explicit node budget exhausted; no accepted assignment, visited_nodes=budget, not an infeasibility proof. |
| InvalidInput exception | Malformed source/policy/receipt/context; no result accepted. Internal verified-allocation invariant failure raises RuntimeError. |

**CV07 — exact receipt.** Allocation fields: profile, dataset_id, input_digest, k, required_support, node_budget, visited_nodes, greedy_choices, status, assignments, objective, reason, policy_digest, receipt_version=SYNTHETIC_ALLOCATION_RECEIPT_V2, exact limitations tuple. Feasible objectives contain three nonnegative exact ints; assignments are sorted unique (synthetic ID, exact int fold) tuples. Non-search status cannot claim visited nodes; search status needs≥1; every counter/reason/status is compared with deterministic recomputation. Canonical JSON validates shape/internal policy only; it does not verify against source, intended request, historical execution or authorization.

`verify_allocation(original_dataset,candidate,expected_policy=retained_policy)` revalidates source, binds input/policy identities and recomputes the complete operation. Malformed/mismatched candidates raise InvalidInput. A correctly reproduced infeasible/undetermined receipt returns False; only correctly reproduced FEASIBLE returns True. No use of truthy serialized strings as acceptance. ## 4. Trust, cost and implementation limits

**CV09 — independently retained expectations.** Expected registry/policy/role choices must come from an owning synthetic fixture controller, retained before candidate construction and outside candidate substitution. Canonical SHA256 binds caller-declared content and detects mismatches against separately retained content; it supplies no keyed verification, signature, trusted storage, scientific truth, human authority or resource permission. Frozen dataclasses are cooperative. Replacing both source/expectation and candidate can pass; deliberate same-process mutation is not sandboxed. Input truth, actual source/transform execution, fit/selection/initialization/exposure evidence and producer identity are outside present verification. These limits are acceptable for controlled synthetic-only engineering with external ownership, never as real split eligibility certification.

**CV10 — bounded reuse without cache.** 17I factors `_allocate_validated` and `_verify_allocation` privately. Each public allocate, verify, role_plan or fit check performs one fresh validate_dataset and one allocation computation. Within the call, receipt replay and role construction consume that fresh registry, removing two redundant registry passes from fit checks. No cross-call cache, caller invalidation token or public trusted-registry parameter is introduced. Every subsequent fit call repeats validation and bounded allocation, detecting changed version/annotation/policy/receipt/roles. Cooperative nonmutation during a call is assumed, as before; concurrent hostile mutation is outside this contract. Tests: `tests/synthetic_mission17d/test_mission17g_hardening.py:472-503` (`test_17i_each_public_cv_operation_validates_once_and_recomputes`); `tests/synthetic_mission17d/test_mission17g_hardening.py:507-521` (`test_17i_repeated_fit_calls_do_not_reuse_stale_context`); `tests/synthetic_mission17d/test_mission17g_hardening.py:524-533` (`test_17i_prevalidated_caller_object_is_not_a_public_trust_shortcut`).

Let V denote complete registry/DAG validation plus canonicalization (including sorting and serialized payload), M development groups, K folds, L labels, U support rules. Greedy candidate scoring has O(M*K*(L+1)) arithmetic evaluations under constant membership-cost abstraction; this implementation also uses tuple label membership in validation/objective checks, with up to O(M*K*U*L + M*L²) simple-operation work there. Group sorting costs O(M log M). Dictionaries/sets/heaps/payload copies and alias/parameter sorting contribute V and linear-in-registry storage; this is not an O(M)-only end-to-end bound. Greedy solver storage includes O(M+K*L); result O(M). DFS additionally retains per-depth remaining/member/used collections, bounded by O(M²+K*L) live objects with M≤18; registry storage remains separate. Bounded DFS can be exponential before its node cap; each node incurs support/pruning/slice work, so node_budget is not a CPU-time limit. Exact integer bit cost is additional. Q fit checks repeat Q*(V+allocation work); they are not O(1) membership queries. M=1536,K4 test profiles show6144 candidate evaluations per operation, repeated on the next call. Do not infer adversarial resource resistance.

**CV11 — implemented versus specified.** Implemented/tested: constructed registry validation, event grouping, explicit unknown metadata, canonical receipt/request binding, heuristic/bounded allocation, role proposals, no-fallback and unverified OOF denial. Specified but unimplemented: authentic corpus registry, duplicate-resolution evidence, exposure/initialization/fit artifact DAG, verified inner-OOF score lineage and calibrator proof, deployment trust, real loaders and official split writer. No scientific corpus independence claim is made.

**CV12 — future 18B acceptance.** Build only explicitly authorized synthetic provenance adapters first: retain source/policy separately; reject alias/capture/annotation/DAG substitutions, duplicates, role swaps, wrong expected policy, forged counters and stale reuse; exercise all six statuses and bounded costs; compare tiny independent feasibility and dense-score oracles; prove no real loader/write/fitting route. Future fitted-artifact/OOF machinery needs its own scoped tests and authentic inputs before enabling anything currently denied. Existing `test_small_cv_exhaustive_oracle_2704_inputs`, `test_incremental_greedy_scores_match_dense_recomputation_50_inputs`, `test_complete_receipt_contract_for_every_status` and the six former failure cases remain passing synthetic evidence, not completed integration. **Never silently reassign/merge event IDs, permit ungrouped fallback, reuse under changed policy, or call a feasible synthetic allocation an approved scientific split.
